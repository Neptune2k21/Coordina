## Levels

Each behaviour is tested at one level: the lowest one that can catch the bug.

| Level | What it proves | Where | Needs |
| --- | --- | --- | --- |
| Graph engine | Algorithms, the C ABI, memory safety | `tests/graph-engine` | g++ |
| API unit | One rule or calculation, without starting the API | `tests/api-unit` | Nothing |
| API integration | A request through the real API and PostgreSQL: access rules, persistence, concurrency, migrations | `tests/api-integration` | Docker |
| Web | Components and state | `src/web/src/**/*.test.tsx` | Nothing |
| End to end | The few user flows that cross every layer | `src/web/e2e` | Docker, Chromium |

To place an API test, ask whether it needs the API running or a database. If it
does, it is an integration test. `tests/api-unit` does not reference the test
host, so it cannot start the API by accident.

The quality tool and the analyzers have their own tests in `tests/quality` and
`tests/analyzers`.

## Rules

- **A test creates the data it needs**, and only looks at that data. It never
  counts the rows of a whole table, because other tests share it.
- **A test waits for a state, not for a delay.** When time matters, it controls
  the clock through `TimeProvider`.
- **A flaky test is a bug.** Fix its cause instead of adding a retry.
- **A bug fix comes with the test that would have caught it.**
- **No code in `src` exists only for tests.** There is one implementation of
  each store, the PostgreSQL one, and the tests run it.
- **A test that measures time runs alone**, in the `TimingTestGroup` collection,
  with a bound loose enough for a slow machine.

## Commands

| Command | What it runs |
| --- | --- |
| `make api-test-unit` | API unit tests, without Docker |
| `make api-test-integration` | API integration tests |
| `make api-test` | Every .NET test, with coverage collected in `TestResults` |
| `make graph-engine-test` | Native engine tests |
| `make web-test` | Web tests |
| `make web-e2e` | End-to-end tests |
| `make verify` | Only the suites your changes can break |
| `make quality` | Everything, as before a merge |

## Test database

Integration tests use the PostgreSQL of `docker/compose.test.yml`. The make
targets start it when they need it, and it stays up between runs.

| Command | Effect |
| --- | --- |
| `make docker-test-up` | Starts it. Do this once before running the tests from an editor |
| `make docker-test-down` | Stops it and discards its data |

It is separate from the development database in every way: its own Compose
project, container, port (`5433`) and credentials. Its files live in memory, so
it starts empty each time. If the port is taken, choose another one for the
whole command:

```bash
POSTGRES_TEST_PORT=5544 make api-test
```

The first run migrates a template database, named after the migrations' SQL.
Each test class then gets its own copy of that template, dropped when the class
ends. Changing a migration changes the name, so a stale template is never
reused. Classes run in parallel, and the tests of one class share its database.

Without the database, integration tests fail at once and say to run
`make docker-test-up`. A run that is killed leaves its databases behind;
`make docker-test-down` removes them.

## End-to-end tests

`make web-e2e` runs them, and passes `args` to Playwright:

```bash
make web-e2e args="--ui"
make web-e2e args="board-drag --repeat-each 10"
```

Playwright starts everything: the test database, the API on port `5051` with a
new `coordina_e2e` database, and the web app on port `5174`. The API's settings
come from the Makefile (`E2E_ENV`) instead of `.env`, so a run never reads or
writes the development database. A server that already uses one of these ports
makes the run fail, since it could serve other code or another database.

## Writing an integration test

Test classes derive from `ApiTest`, which provides:

| Member | Use |
| --- | --- |
| `Api` | An `ApiTestClient`, to register users, build a scenario and send requests |
| `Database` | SQL on the class's database, for what the API does not show |
| `Factory` | The running API, to resolve a service or replace one |

`BoardScope` creates an owner, a workspace, a project and a board in one line.
A setup request that fails reports its method, URL, status and body. The records
in `tests/api-integration/Support/ApiContracts.cs` mirror the JSON the web client
receives.

Check the result through the API first. Every board write answers with the board
read back from PostgreSQL, so the response already proves what was stored. Use
`Database` for what only SQL shows: row counts after a race, a constraint, a
rollback.

Migration tests do not need the API. They ask `TestDatabaseServer` for an empty
database, or for one stopped at an earlier migration.

## Graph engine benchmark

`make graph-engine-benchmark` builds deterministic sparse dependency graphs and
measures a full board analysis two ways: the six individual native calls the API
used to make, and the single `coordina_graph_analyze_board` call it makes now. It
also checks that both produce the same ranking and fails if they differ.
`make test` runs a smoke pass at 100 and 1,000 nodes. There is no timing
threshold, so a slow CI runner cannot fail the build.

Pass `sizes="100 500"` to choose graph sizes.

Median timings recorded on a development laptop (`-O2`). Use them for relative
comparison only:

| Nodes | Before: individual calls | After: individual calls | After: batch call |
| --- | --- | --- | --- |
| 100 | 0.62 ms | 0.47 ms | 0.14 ms |
| 1,000 | 8.1 ms | 5.1 ms | 0.82 ms |
| 10,000 | 188 ms | 61 ms | 31 ms |

The batch call builds the graph snapshot and topological order once and reuses
them. Transitive dependent counts use one backward pass over the topological
order with per-node bitsets, instead of a traversal per node. Graphs larger than
16,384 nodes fall back to traversal to bound memory.

## Manual smoke flow

1. Register or sign in at `/login`.
2. Open `/app`.
3. Create a workspace and confirm the owner role.
4. Open `/app/projects` and create a project.
5. Archive it and confirm it is hidden by default.
6. Enable archived projects and confirm the status badge appears.
7. Mark a project completed and confirm edits are blocked.
8. Generate an invitation code, sign in as another user, and redeem it once.
9. Confirm only workspace owners or project owners can edit and archive.
10. Confirm a non-member receives `404` for workspace and project details.
11. Open a board, move a card into the last list, and confirm it shows as completed.
12. Rename that list and confirm the board metrics do not change.
