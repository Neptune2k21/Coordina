A project's work lives in its board. A board has lists, and a list holds cards.
Cards are the only representation of project work: there is no separate task
store.

## Workflow status

Every list has an explicit `taskStatus`, borrowed from Jira's status categories:

| Status | Meaning |
| --- | --- |
| `TODO` | Not started |
| `IN_PROGRESS` | Being worked on. WIP limits apply here |
| `DONE` | Delivered |

The status is set when the list is created and is never inferred from the title.
Renaming "Done" to "Shipped" changes nothing about the cards in it.

| How the list is created | Status |
| --- | --- |
| `BASIC` template | To Do `TODO`, In Progress `IN_PROGRESS`, Done `DONE` |
| `AGILE_SCRUM` template | Backlog `TODO`, Sprint Backlog `TODO`, In Progress `IN_PROGRESS`, Review `IN_PROGRESS`, Done `DONE` |
| `BUG_TRACKING` template | Reported `TODO`, Investigating `IN_PROGRESS`, Verifying `IN_PROGRESS`, Released `DONE` |
| `PRODUCT_ROADMAP` template | Ideas `TODO`, Planned `TODO`, In Progress `IN_PROGRESS`, Shipped `DONE` |
| `CUSTOM` board | First list `TODO`, last list `DONE` (when there are at least two), others `IN_PROGRESS` |
| `BLANK` board | No lists |
| `POST .../lists` | `taskStatus` from the request, default `TODO` |

## Card completion

A card is completed exactly when it sits in a `DONE` list.

| Action | Result |
| --- | --- |
| Create a card in a `DONE` list | Created completed |
| Move a card into a `DONE` list | Completed, `completedAt` and `completedBy` set |
| Move a card out of a `DONE` list | Reopened, completion fields cleared |
| `PATCH` with `isCompleted: true` | Moved to the first `DONE` list |
| `PATCH` with `isCompleted: false` | Moved to the first `TODO` list |
| No list with the target status | `409 Conflict`; the card is not changed |

## Planning

The planning panel recommends what to do next. The native graph engine ranks
open cards with fixed, explainable rules:

| Signal | Effect |
| --- | --- |
| Due date, priority, dependency impact, critical path, subtask progress | Existing base score |
| Each unfinished dependency | Large penalty; blocked cards are never the primary suggestion |
| Card in an `IN_PROGRESS` list | Bonus: finish what is started |
| Assigned to you | Bonus |
| Assigned only to someone else | Penalty (still listed) |
| Has the selected context label | Bonus |
| Size fits the selected focus slot | Bonus |
| Size bigger than the focus slot | Penalty |
| No size with a focus slot | No bonus, no penalty, shown as "Size unknown" |

Ties break on board position, then card id, so the same board always gives the
same order.

The critical path is the chain of open cards that takes longest, weighted by
the likely duration of each card's size: three `XS` cards in a row weigh less
than one `L`. An unsized card counts as `M`, and completed cards take no part
in it, so a completed card in the middle of a chain cuts it. Only chains of at
least two cards count: a board without open dependencies has no critical path.

### Card sizes

A card is sized rather than estimated: nobody knows whether a task takes 90 or
120 minutes, but everyone can tell a few hours from a few days. A size is an
order of magnitude, and the bigger the card, the wider its range:

| Size | Means | Half the cards take less than | Eight in ten take between |
| --- | --- | --- | --- |
| `XS` | Under an hour | 30 min | 15 min – 1 h |
| `S` | A few hours | 2 h | 1 h – 4 h |
| `M` | About a day | 1 day | ½ day – 2 days |
| `L` | A few days | 3 days | 2 – 4½ days |
| `XL` | About a week | 5 days | 3 – 7½ days |
| `XXL` | More than a week | 8 days | 4 – 16 days, and the card should be split |

A day is 6 hours of focus work. The ranges live in one place, the graph engine
(`src/graph-engine/src/planning/card_size.cpp`); the API and the web app only
handle the codes.

Set `size` on create or update; clear it with `clearSize: true`. Unknown codes
return `400`.

### Focus slot

```http
GET /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/graph
    ?maxSize=S&context=backend&preferAssigned=true&includeUnassigned=true
```

| Parameter | Values | Default |
| --- | --- | --- |
| `maxSize` | The biggest size that fits the slot: `S` for a quick task, `M` for half a day; leave it out for any size | any size |
| `context` | A label; `#` and spaces are normalized, max 32 characters | none |
| `preferAssigned` | `true` / `false` | `true` |
| `includeUnassigned` | `true` / `false` | `true` |

Invalid values return `400`. Each plan item includes structured explanation
fields: `size`, `fitsMaxSize`, `isAssignedToMe`, `isContextMatch`,
`isInProgress`, and `isShortestAlternative`. When nothing ready fits the focus
slot, the smallest sized ready card is flagged `isShortestAlternative`.

## Milestones

A milestone is a card with a target date, such as "Launch v1" or "Demo day".
Its scope is the card and every open card it depends on, through open cards:
the dependency graph defines it, so there is nothing to tag. Work behind a
completed card is not needed any more. A milestone without dependencies covers
only itself.

```http
PATCH /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/cards/{cardId}
      { "milestoneDate": "2027-03-12" }
PATCH /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/cards/{cardId}
      { "clearMilestoneDate": true }
GET   /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/milestones
```

A new milestone date cannot be in the past (`400`); a milestone whose date has
passed keeps it until someone moves or clears it. Anyone who can read the
project can read the forecasts.

### How the forecast works

The graph engine (`coordina_graph_forecast`) simulates the work of all the
board's open milestones together, 2,000 times: they share one team, so a person
busy on the first is late on the second.

1. **Durations.** Each run draws how long every open card takes.
   - A size is a log-normal range: a card can take three times its likely time,
     never three times less than nothing.
   - How far this team is off shifts that range. **Each run draws that shift
     once for all its cards**: when a
     team is slow, every card is. Without this, slips would cancel out and a
     85% date would be met about six times in ten.
   - A few cards run away from their size altogether. Past a threshold the
     duration follows a power law, as measured on IT projects.
   - An unsized card draws its size first, from the sizes the board's other
     cards have. Not knowing a size makes a forecast wider, not equal to an `M`.
   - A card in progress is drawn given the time it already took. The longer it
     drags past its range, the likelier it has run away, and what is left grows.
2. **Order.** Cards in progress come first, then those that can start latest
   without making a milestone late, counting back from every target through the
   chains of cards that wait for each other and through the cards that wait for
   the same person. Priority only breaks ties: everything in a scope has to
   ship. The order is computed, not searched, so it is stable, and it comes
   within a few percent of a bound no plan beats (`make graph-engine-lab`).
3. **People.** A person works 6 focus hours a day on one card at a time, and a
   card starts once its open dependencies are done. It goes to one of its
   assignees who is free, or to anyone of the team when it has none: to whoever
   has least work of their own left, so a bottleneck keeps to its own cards. The
   team is everyone assigned to an open card of the board, or one person when
   nobody is. Cards in progress outside the scopes keep their people busy first.
4. **Results.** Dates count working days from today, skipping weekends. Each
   card has a random stream of its own, keyed by its id and a fixed seed: the
   forecast only moves when something it depends on changes.

The runs spread over the cores other requests leave free and give the same
result with any number of threads. On the benchmark board
(`make graph-engine-benchmark`), 2,000 runs over 1,000 cards take about 26 ms on
20 cores and 260 ms on one.

| Field | Meaning |
| --- | --- |
| `targetDate` | The milestone's date |
| `status` | `ON_TRACK` (P85 on or before the target), `AT_RISK` (P50 on time, P85 late), `LATE` (P50 late), `OVERDUE` (target passed), `COMPLETED` |
| `forecastDate`, `commitDate` | P50 and P85 dates; `null` once completed |
| `bestCaseDate`, `worstCaseDate` | P10 and P95 dates |
| `unlimitedTeamDate` | The P50 date with as many people as it takes: no staffing beats it |
| `onTime` | The chance of being done by the target, from 0 to 1 |
| `slipDays` | `forecastDate` minus `targetDate`, in calendar days; positive is late |
| `openCardCount`, `unsizedCardCount` | Open cards in the scope, and those without a size |
| `drivers` | Up to three cards, other than the milestone, that set the date in at least one run in ten, most critical first. `criticality` is that share of runs; `sensitivity` is the correlation between the card's own uncertainty and the date, so squared it is the share of the date's spread that sizing or splitting the card can remove |

### Limits

The forecast is as good as what the board says, and it knows nothing else:

- Every person gives 6 focus hours a day, every weekday. Holidays, time off
  and part-time work are not counted.
- Work outside the board takes nobody's time, and neither do cards outside
  every scope until someone starts them. A team busy elsewhere makes the
  forecast optimistic.
- A card started while it waits for another one is planned after that one.
- The ranges are Coordina's own, the same for every team. They are wide on
  purpose: teams that estimate 40% too low still meet an 85% date about 60% of
  the time. Those figures come
  from simulated teams (`make graph-engine-lab`), not from real ones yet.

### Cutting the scope

When a milestone is at risk or late, the engine can propose what to take out
so it ships on time, and say what a cut buys before anyone applies it.

```http
POST /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/milestones/{milestoneId}/scope-proposal
     { "keep": ["..."] }
POST /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/milestones/{milestoneId}/scope-evaluation
     { "cardIds": ["..."] }
POST /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/milestones/{milestoneId}/scope-cut
     { "cardIds": ["..."] }
```

Taking a card out also takes out the cards of the scope that depend on it,
since they cannot ship without it, and the cards the milestone then no longer
needs. A card it still needs through another path stays. Applying a cut
(`scope-cut`) removes the milestone's dependencies on the cards that leave;
nothing is deleted, and the cards stay on the board. The proposal and the
evaluation change nothing, and anyone who can read the project can ask for
them; applying a cut needs write access. A done milestone, or one whose target
has passed, cannot be cut (`400`).

**What a proposal aims for.** The best chance of shipping by the target date,
reaching 85% if it can, while giving up as little value as possible. A card
is worth its priority, whatever its size: high 4, medium 2, low or none 1. Its
size says what it costs, not what it is worth. The milestone, cards in progress, the `keep` cards, and any card whose cut
would take one of them out are never proposed. When a card is needed by only
one other card of the scope, the proposal names that other card: cutting
either takes both out.

**How the engine searches** (`coordina_graph_propose_scope`). Choosing what to
cut under dependencies is a knapsack with precedence constraints, which is
NP-hard, so the engine uses a heuristic:

1. **Greedy batches.** Cut the cards that give up least value per hour saved,
   until their savings would bring the 85% date to the target, then simulate
   again, since cards that waited behind them may now set the date. The hours
   a card saves are its share of the chain that sets the date in each run:
   that chain spans the whole run, so the shares add up to the mean finish.
2. **Local search.** Give back each cut the goal no longer needs, those that
   give up most value per hour first, then try to trade each cut for a cheaper
   one.
3. **Confirmation.** Candidates are compared on 256 runs, on the cards' own
   random streams, so two candidates differ only by what they cut. When the
   result falls short of 85% on the forecast's 2,000 runs, up to three more
   batches repair it, each kept only if it raises the chance.
4. **Forecast.** The board is forecast again without the cards that leave. What
   the proposal announces is what the milestone shows once it is applied, and a
   cut that does not help there is not proposed.

The search stops after 450 ms; forecasting the scope before and after comes on
top on a slow machine. On the benchmark board, 1,000 cards take about 450 ms on
20 cores (`make graph-engine-benchmark`). The same board gives the
same proposal with any number of threads, unless the time limit stops the
search first.

| Field | Meaning |
| --- | --- |
| `onTimeBefore`, `onTimeAfter` | Share of runs done by the target date, from 0 to 1, without and with the cut |
| `forecastDate`, `commitDate` | P50 and P85 dates of the work left |
| `cuts` | The cards to take out, each with `alsoRemoved`: the cards that leave with it. Empty when nothing is worth cutting |

The banner shows **Propose a scope** on milestones at risk or late. Unchecking
a card measures the others again; **Take out** applies the cut.

**Limits.** The proposal shares the forecast's limits, and:

- A card's value is its priority; the engine does not know what matters to
  customers beyond that. Unchecking a card, or keeping it, is how
  someone says so.
- When 85% cannot be reached, the proposal is the best chance it found. It
  proposes nothing when no cut raises the chance at all.
- It only cuts whole cards. Splitting a large card can also save a date; the
  engine does not suggest it yet. Moving work to someone else is what
  [Who does what](#who-does-what) proposes.

### Who does what

On any milestone with work left, the engine can propose who should take which
card so it ships sooner, as a list of changes to accept one by one.

```http
POST /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/milestones/{milestoneId}/staffing-proposal
     { "people": ["..."], "allowReassignment": false }
POST /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/milestones/{milestoneId}/staffing-evaluation
     { "changes": [{ "cardId": "...", "userId": "..." }] }
POST /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/milestones/{milestoneId}/staffing
     { "changes": [{ "cardId": "...", "userId": "..." }] }
```

A change gives a card to one person, who becomes its only assignee: applying
it (`staffing`) changes the card's assignees and nothing else. The proposal
and the evaluation change nothing, and anyone who can read the project can
ask for them; applying needs write access, and only open cards of the board
can be given (`400`). Everyone named must belong to the workspace (`400`). A
done milestone cannot be planned (`400`).

**What a proposal looks for.** The plan that ships the milestone soonest: its
85% date first, then its 50% one, without making the board's other milestones
late for it (`othersDelayDays`). The constraints:

- A card only goes to one of `people`. Without them, the proposal plans with
  the people assigned to open cards of the board, or with the whole
  workspace when nobody is.
- A card that has assignees stays with them unless `allowReassignment` is
  set. A card in progress never moves.
- A card goes preferably to someone who has completed cards with one of its
  labels (an assignee of a done card, or whoever completed it when it had
  none). Giving it to someone else costs the plan two focus hours: it only
  happens when that ships the milestone sooner than that.
- Taking a card off someone costs the plan half a day, for the handover, and
  giving one nobody has a quarter of an hour: a plan of forty changes is not one
  anybody applies.

**The dates are the forecast's.** The plan found is measured by forecasting the
board with it. The team is whoever is assigned to an open card, and only they
pick up unassigned cards. Giving a card to someone outside the team brings them in;
taking someone's last card off them takes them out. So the dates after a
proposal are the ones the milestone shows once it is applied, to the day.

**How the engine searches** (`coordina_graph_propose_staffing`). Assigning
cards to people under dependencies is resource-constrained project
scheduling, which is NP-hard, so the engine uses a heuristic:

1. **Simulated annealing.** Four chains each change who takes one card at a
   time, half the time a card on the chain that sets the date. A change that
   makes the plan worse is kept less and less often as the search cools. Two
   chains start from the current plan, two from everyone in `people` picking
   up unassigned cards, which finds idle people quickly.
2. **Screening.** Plans are compared on 8 runs drawn once from the cards' own
   streams, so a plan that leaves room to absorb a slip beats one that only
   fits the median durations.
3. **Pruning and forecast.** The best plan gives back every change it does not
   need, then the board is forecast with it. When it would not bring a date in by
   more than it delays the other milestones, the proposal has no change.

The chains always split the same way, so the same board gives the same
proposal with any number of threads, unless the time limit stops the search
first: the whole proposal takes at most 800 ms. On the benchmark board with
eight people and reassignment allowed (`make graph-engine-benchmark`), 500
cards take about 670 ms on 20 cores and bring the 85% date from 444 to about
320 working days with 94 changes; 1,000 cards stay under 800 ms.

| Field | Meaning |
| --- | --- |
| `forecastDateBefore`, `commitDateBefore` | P50 and P85 dates of the plan as it is: the milestone's forecast |
| `forecastDateAfter`, `commitDateAfter` | The same dates once the changes are applied |
| `people` | Who the proposal could give cards to |
| `changes` | Each card to give: `from` (its assignees now, empty when none), `to`, `startBefore` and `startAfter` (the day it starts if every card takes its likely time) and `matchingLabels` (its labels its new person has completed cards with). Empty when no better plan exists |

The banner shows **Optimize the plan** on every milestone with work left. The
dialog says how many days sooner the plan ships, then each change with its
reason: when the card can start, whom it frees, and what its person has done
before. Choosing who to plan with, or letting assigned cards move, asks again;
unchecking a change measures the others; **Apply** gives the cards.

**Limits.** The proposal shares the forecast's limits, and:

- It never uses that one person is faster than another: the search plans every
  card at its median time. Only the final forecast counts what the board has
  learned about who does it.
- Skills are labels: a person who has done `backend` cards is preferred for
  the next one, but the engine does not know who is learning, who is senior,
  or who is on holiday.
- With many people and many cards, it can propose many changes. Each one
  helps the plan, but the dialog is the place to keep only those the team
  agrees with.

## Concurrent changes

Adding a dependency runs under a per-board lock (`IBoardStore.RunExclusiveAsync`), so the cycle check and the write cannot interleave with another request. When two requests would close a cycle together, one succeeds and the other gets `409`. Sending the same dependency several times stores it once, and every request succeeds.

Creating a list, a card or a subtask, and moving or completing a card, take the same lock, because the new position is the current maximum plus one. Cutting a milestone's scope takes it too, so the dependencies it removes are the ones it measured, and so does giving cards to people from a milestone's plan. Rows that already share a position, from before this lock, are ordered by creation time and then id, so they always load in the same order.

## Project shell and board system

Each project detail page is a container, not a single-purpose board screen. The shell owns project metadata and module navigation, while each module owns its data and state.
### One board per project

For v0, a project has exactly one board: the project page shows it, and nothing lets a user pick another. `POST .../boards` returns `409` when the project already has one, including when two requests race, because a unique index on `boards.project_id` decides. The web app then loads the existing board instead of showing an error.

The `OneBoardPerProject` migration keeps the oldest board of each project, which is the one the app was already showing, and deletes the others with their lists and cards. Several boards per project can come back later, with a way to choose between them.

### Board templates

Project creation intentionally does not choose the board workflow. When a new project is opened for the first time, the board module shows a setup screen where the user can choose a template or create custom lists.

`BoardTemplateCatalog` in the API is the only definition of templates. `GET /board-templates` returns each one (id, name, summary, lists with their status, and example cards), and the setup screen renders its preview from that response. To change a template, edit the catalog; the web app needs no change.

| Template | Generated lists (status) | Intent of the lists |
| --- | --- | --- |
| `BASIC` | To Do (`TODO`), In Progress (`IN_PROGRESS`), Done (`DONE`) | The three statuses and nothing else, for small pieces of work. |
| `AGILE_SCRUM` | Backlog (`TODO`), Sprint Backlog (`TODO`), In Progress (`IN_PROGRESS`), Review (`IN_PROGRESS`), Done (`DONE`) | Sprint Backlog is committed work nobody has started, so it is still `TODO`. Review is not finished until it is accepted, so it is still `IN_PROGRESS`. |
| `BUG_TRACKING` | Reported (`TODO`), Investigating (`IN_PROGRESS`), Verifying (`IN_PROGRESS`), Released (`DONE`) | Verifying holds fixes being confirmed before release. A bug is only `DONE` once customers have the fix. |
| `PRODUCT_ROADMAP` | Ideas (`TODO`), Planned (`TODO`), In Progress (`IN_PROGRESS`), Shipped (`DONE`) | Ideas are not committed, Planned are. Neither has started, so both are `TODO`. |
| `CUSTOM` | First list `TODO`, last list `DONE` (when there are at least two), remaining lists `IN_PROGRESS` | The user names the lists. Custom boards never have example cards. |
| `BLANK` | None | The user builds the board list by list and picks each list's status. Cards can only be completed once the board has a `DONE` list. |

`CUSTOM` and `BLANK` are not in `GET /board-templates`, because they have no content to return. The setup screen offers them directly.

`POST .../lists` accepts an optional `taskStatus`, defaulting to `TODO`. The form for adding a list lets the user choose it.

#### Example cards

By default, a board created from a template includes example cards, so planning has something to show on day one: ready and blocked work, a critical path, and a next-task ranking. Each card has a description, labels, a priority, and an effort estimate. Some also have subtasks, dependencies on other cards in the template, and a due date relative to the day the board is created.

Send `"includeExampleCards": false` to get the same lists with no cards. The setup screen offers this as a checkbox.

Tests hold every template to these rules:

- Every status has at least one list.
- Card keys are unique, and every dependency points to a card in the same template.
- The dependency graph is acyclic, and a card is never further along than a card it waits for.
- `IN_PROGRESS` lists stay within the WIP limit.
- A new board has a non-empty next-task ranking.

Each list in a board response includes `taskStatus`:

```json
{
  "id": "4f0c…",
  "title": "In Progress",
  "position": 1,
  "taskStatus": "IN_PROGRESS",
  "cards": []
}
```
### Board permission rules

Board access is verified through the parent project and workspace.

| Action | Server-side rule |
| --- | --- |
| Fetch board | Authenticated workspace member and project in that workspace |
| Create board | Authenticated workspace member and valid template |
| Create/update list | Authenticated workspace member |
| Create/update card | Authenticated workspace member |
| Move card | Authenticated workspace member and target list in the same board |
| Assign card | Every assignee must be a workspace member |
| Delete card | Workspace `OWNER` or project owner |
| Comment on a card | Authenticated workspace member |
| Edit a comment | Its author only (`403` for anyone else, owners included); records `editedAt` |
| Delete a comment | Its author or a workspace `OWNER` (`403` otherwise) |
| Cross-project access | Hidden behind `404` responses |
| Non-member access | Hidden behind `404` responses |

The board fetch endpoint returns the full board structure in one request: board, lists, cards, labels, and assignees. The persistence layer loads these with batched queries rather than per-card lookups, leaving room for pagination or virtualized lanes if board sizes grow.

Completed projects remain read-only for board mutations, matching the project lifecycle rule enforced by the projects module.

## Rules

- Every route validates workspace membership and that the project belongs to the
  workspace. Foreign or mismatched ids receive `404`.
- Completed projects are read-only for board mutations (`409`).
- Assignees must be workspace members.
- Deleting a card requires a workspace owner or project owner.
- Only its author edits a comment, so it keeps saying what they wrote; its
  author or a workspace owner deletes it. An edited comment carries `editedAt`,
  shown as "(edited)".
