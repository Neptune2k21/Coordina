A project's work lives in its board. A board has lists, and a list holds cards.
Cards are the only representation of project work: there is no separate task
store.

## Workflow status

Every list has an explicit `taskStatus`, borrowed from Jira's status categories:

| Status | Meaning |
| --- | --- |
| `TODO` | Not started |
| `IN_PROGRESS` | Being worked on. WIP limits apply here |
| `DONE` | Delivered |

The status is set when the list is created and is never inferred from the title.
Renaming "Done" to "Shipped" changes nothing about the cards in it.

| How the list is created | Status |
| --- | --- |
| `BASIC` template | To Do `TODO`, In Progress `IN_PROGRESS`, Done `DONE` |
| `AGILE_SCRUM` template | Backlog `TODO`, Sprint Backlog `TODO`, In Progress `IN_PROGRESS`, Review `IN_PROGRESS`, Done `DONE` |
| `BUG_TRACKING` template | Reported `TODO`, Investigating `IN_PROGRESS`, Verifying `IN_PROGRESS`, Released `DONE` |
| `PRODUCT_ROADMAP` template | Ideas `TODO`, Planned `TODO`, In Progress `IN_PROGRESS`, Shipped `DONE` |
| `CUSTOM` board | First list `TODO`, last list `DONE` (when there are at least two), others `IN_PROGRESS` |
| `BLANK` board | No lists |
| `POST .../lists` | `taskStatus` from the request, default `TODO` |

## Card completion

A card is completed exactly when it sits in a `DONE` list.

| Action | Result |
| --- | --- |
| Create a card in a `DONE` list | Created completed |
| Move a card into a `DONE` list | Completed, `completedAt` and `completedBy` set |
| Move a card out of a `DONE` list | Reopened, completion fields cleared |
| `PATCH` with `isCompleted: true` | Moved to the first `DONE` list |
| `PATCH` with `isCompleted: false` | Moved to the first `TODO` list |
| No list with the target status | `409 Conflict`; the card is not changed |

## Planning

The planning panel recommends what to do next. The native graph engine ranks
open cards with fixed, explainable rules:

| Signal | Effect |
| --- | --- |
| Due date, priority, dependency impact, critical path, subtask progress | Existing base score |
| Each unfinished dependency | Large penalty; blocked cards are never the primary suggestion |
| Card in an `IN_PROGRESS` list | Bonus: finish what is started |
| Assigned to you | Bonus |
| Assigned only to someone else | Penalty (still listed) |
| Has the selected context label | Bonus |
| Effort fits the selected focus time | Bonus |
| Effort longer than the focus time | Penalty |
| Effort unknown with a focus time | No bonus, no penalty, shown as "Effort unknown" |

Ties break on board position, then card id, so the same board always gives the
same order. A board without dependencies has no critical path.

Cards carry an optional effort estimate, `estimatedMinutes` (5–2,880). Set it on
create or update; clear it with `clearEstimatedMinutes: true`.

```http
GET /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/graph
    ?availableMinutes=60&context=backend&preferAssigned=true&includeUnassigned=true
```

| Parameter | Values | Default |
| --- | --- | --- |
| `availableMinutes` | `0` (no limit) or 5–2,880 | `0` |
| `context` | A label; `#` and spaces are normalized, max 32 characters | none |
| `preferAssigned` | `true` / `false` | `true` |
| `includeUnassigned` | `true` / `false` | `true` |

Invalid values return `400`. Each plan item includes structured explanation
fields: `estimatedMinutes`, `fitsAvailableTime`, `isAssignedToMe`,
`isContextMatch`, `isInProgress`, and `isShortestAlternative`. When nothing ready
fits the focus time, the ready card with the smallest known estimate is flagged
`isShortestAlternative`.

## Concurrent changes

Adding a dependency runs under a per-board lock (`IBoardStore.RunExclusiveAsync`), so the cycle check and the write cannot interleave with another request. When two requests would close a cycle together, one succeeds and the other gets `409`. Sending the same dependency several times stores it once, and every request succeeds.

## API surface

```http
GET    /board-templates
GET    /workspaces/{workspaceId}/projects/{projectId}/board
POST   /workspaces/{workspaceId}/projects/{projectId}/boards
       { "name": "Delivery", "template": "CUSTOM", "customListTitles": ["Inbox", "Build", "Live"] }
       { "name": "Sprint 12", "template": "AGILE_SCRUM", "includeExampleCards": false }
POST   /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/lists
       { "title": "Review", "taskStatus": "IN_PROGRESS" }
PATCH  /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/lists/{listId}
       { "title": "Code review" }
POST   /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/lists/{listId}/cards
PATCH  /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/cards/{cardId}
       { "isCompleted": true }
PATCH  /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/cards/{cardId}/move
       { "listId": "..." }
DELETE /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/cards/{cardId}
GET    /workspaces/{workspaceId}/projects/{projectId}/boards/{boardId}/graph
```

## Project shell and board system

Each project detail page is a container, not a single-purpose board screen. The shell owns project metadata and module navigation, while each module owns its data and state.
### Board templates

Project creation intentionally does not choose the board workflow. When a new project is opened for the first time, the board module shows a setup screen where the user can choose a template or create custom lists.

`BoardTemplateCatalog` in the API is the only definition of templates. `GET /board-templates` returns each one (id, name, summary, lists with their status, and example cards), and the setup screen renders its preview from that response. To change a template, edit the catalog; the web app needs no change.

| Template | Generated lists (status) | Intent of the lists |
| --- | --- | --- |
| `BASIC` | To Do (`TODO`), In Progress (`IN_PROGRESS`), Done (`DONE`) | The three statuses and nothing else, for small pieces of work. |
| `AGILE_SCRUM` | Backlog (`TODO`), Sprint Backlog (`TODO`), In Progress (`IN_PROGRESS`), Review (`IN_PROGRESS`), Done (`DONE`) | Sprint Backlog is committed work nobody has started, so it is still `TODO`. Review is not finished until it is accepted, so it is still `IN_PROGRESS`. |
| `BUG_TRACKING` | Reported (`TODO`), Investigating (`IN_PROGRESS`), Verifying (`IN_PROGRESS`), Released (`DONE`) | Verifying holds fixes being confirmed before release. A bug is only `DONE` once customers have the fix. |
| `PRODUCT_ROADMAP` | Ideas (`TODO`), Planned (`TODO`), In Progress (`IN_PROGRESS`), Shipped (`DONE`) | Ideas are not committed, Planned are. Neither has started, so both are `TODO`. |
| `CUSTOM` | First list `TODO`, last list `DONE` (when there are at least two), remaining lists `IN_PROGRESS` | The user names the lists. Custom boards never have example cards. |
| `BLANK` | None | The user builds the board list by list and picks each list's status. Cards can only be completed once the board has a `DONE` list. |

`CUSTOM` and `BLANK` are not in `GET /board-templates`, because they have no content to return. The setup screen offers them directly.

`POST .../lists` accepts an optional `taskStatus`, defaulting to `TODO`. The form for adding a list lets the user choose it.

#### Example cards

By default, a board created from a template includes example cards, so planning has something to show on day one: ready and blocked work, a critical path, and a next-task ranking. Each card has a description, labels, a priority, and an effort estimate. Some also have subtasks, dependencies on other cards in the template, and a due date relative to the day the board is created.

Send `"includeExampleCards": false` to get the same lists with no cards. The setup screen offers this as a checkbox.

Tests hold every template to these rules:

- Every status has at least one list.
- Card keys are unique, and every dependency points to a card in the same template.
- The dependency graph is acyclic, and a card is never further along than a card it waits for.
- `IN_PROGRESS` lists stay within the WIP limit.
- A new board has a non-empty next-task ranking.

Each list in a board response includes `taskStatus`:

```json
{
  "id": "4f0c…",
  "title": "In Progress",
  "position": 1,
  "taskStatus": "IN_PROGRESS",
  "cards": []
}
```
### Board permission rules

Board access is verified through the parent project and workspace.

| Action | Server-side rule |
| --- | --- |
| Fetch board | Authenticated workspace member and project in that workspace |
| Create board | Authenticated workspace member and valid template |
| Create/update list | Authenticated workspace member |
| Create/update card | Authenticated workspace member |
| Move card | Authenticated workspace member and target list in the same board |
| Assign card | Every assignee must be a workspace member |
| Delete card | Workspace `OWNER` or project owner |
| Cross-project access | Hidden behind `404` responses |
| Non-member access | Hidden behind `404` responses |

The board fetch endpoint returns the full board structure in one request: board, lists, cards, labels, and assignees. The persistence layer loads these with batched queries rather than per-card lookups, leaving room for pagination or virtualized lanes if board sizes grow.

Completed projects remain read-only for board mutations, matching the project lifecycle rule enforced by the projects module.

## Rules

- Every route validates workspace membership and that the project belongs to the
  workspace. Foreign or mismatched ids receive `404`.
- Completed projects are read-only for board mutations (`409`).
- Assignees must be workspace members.
- Deleting a card requires a workspace owner or project owner.
